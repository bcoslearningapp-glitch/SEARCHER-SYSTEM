# ADR-007: Sandboxed, content-addressed local object storage
Status: Accepted
Date: 2026-09-24

Context:
PRD §57 asks for a filesystem-backed local object store with an S3-compatible abstraction; SEC-006/007 require validated uploads and file paths sandboxed to configured roots; FR-INGEST-001 requires the immutable original asset to be retained; §81 requires an ADR for the storage abstraction.

Decision:
- `research_api.platform.storage.ObjectStore` protocol (`put`, `read`, `exists`) with a `LocalObjectStore` implementation rooted at `STORAGE_ROOT` (a Docker volume in compose).
- Content addressing: key = `sha256/<aa>/<bb>/<sha256>`. Keys are generated by the store, never from user input; every key is validated by regex and the resolved path must stay inside the root. Files are written atomically and made read-only; identical content is stored once.
- `read` re-hashes content and fails on mismatch, so tampering or corruption is detected before ingestion or export.
- Uploads are size-limited (`MAX_UPLOAD_BYTES`), non-empty, and typed by sniffing bytes (PDF, UTF-8 text, PNG, JPEG, EPUB); client-declared types and filenames are not trusted. Filenames are kept only as sanitized display metadata.
- Deletion is not part of the interface: epistemically meaningful originals are retained (PRD §60.7). Removal will need an explicit, authorized administrative procedure (SEC-009).

Alternatives considered:
- MinIO from day one: extra service for a single-workstation default; the protocol keeps it a drop-in later.
- Path-per-filename layout: invites traversal bugs and duplicate storage.

Consequences:
- An S3/MinIO adapter can implement the same protocol; object keys stay stable across backends.
- Backups must include the storage volume alongside PostgreSQL.

Research Core impact: Preserves original assets and their fingerprints, supporting source identity and verification (Core §23, §45 source hash).

Migration impact: None (no schema).
